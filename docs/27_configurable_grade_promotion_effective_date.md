# 학년 자동승급 기준일 변경 기능

## 1. 변경 전 구조

- `academy_grade_promotion_settings.effective_month/effective_day` 컬럼은 이미 존재했지만 DB CHECK가 `1월 1일`만 허용했습니다.
- 승급 배치 생성 로직도 기준일을 `${promotion_year}-01-01`로 고정했습니다.
- `grade_promotion_batches.effective_date`에는 배치별 적용일이 저장되어 있었으므로, 배치 생성 후 설정이 바뀌어도 기존 배치의 날짜를 보존할 수 있는 구조였습니다.
- 자동 승급은 별도 스케줄러를 새로 만들지 않고 기존처럼 관리자 화면 접근 시 `ensureDueGradePromotion` 흐름에서 처리됩니다.

## 2. 변경 후 구조

- 학원별 설정에 월·일을 저장합니다. 기본값은 기존과 같은 `1월 1일`입니다.
- 새 배치 생성 시 현재 학원 설정을 읽어 `grade_promotion_batches.effective_date`에 날짜를 스냅샷합니다.
- 이미 존재하는 배치를 다시 미리보기하거나 승인·적용할 때는 저장된 `effective_date`를 다시 계산하지 않습니다.
- 기준일 계산은 서버의 `Asia/Seoul` 날짜(`seoulToday`)와 날짜 문자열을 사용하므로 UTC 시각 때문에 기준일이 하루 밀리지 않도록 기존 정책을 유지합니다.

## 3. 관리자 화면 변경 사항

학사 설정 → 학년 자동 승급 화면에 다음 입력을 추가했습니다.

- 월: 1월~12월
- 일: 선택한 월의 유효한 날짜만 표시
- 기본값: 1월 1일
- 2월 29일은 선택 목록에서 제외
- 저장 전 기준일 변경 확인
- 현재 저장 기준일 표시
- 저장 중 중복 클릭 방지

안내 문구에는 “변경된 기준일은 새로 생성하는 승급 배치부터 적용”된다는 정책을 표시합니다.

승급 배치의 적용 기준일은 배치가 있으면 배치에 저장된 날짜를, 아직 배치가 없으면 현재 설정으로 계산해 표시합니다.

## 4. API 변경 사항

`POST /api/admin/academic`의 `resource=grade_promotion_settings` 처리에서 다음을 검증합니다.

- 관리자 인증과 기존 학원 권한 검증 유지
- `effectiveMonth`, `effectiveDay`가 정수인지 확인
- 월 1~12 확인
- 해당 월의 실제 날짜인지 확인
- 2월 29일, 2월 30일, 4·6·9·11월 31일 거부
- 값이 생략되면 기존 저장값을 사용하고, 최초 저장은 1월 1일을 사용

설정과 감사로그는 새 `save_grade_promotion_settings_transaction` DB 함수에서 같은 트랜잭션으로 저장합니다. 감사로그 저장에 실패하면 함수 전체가 실패하여 설정 변경도 커밋되지 않습니다.

## 5. DB migration 내용

신규 migration:

`web/supabase/migrations/20261027134237_configurable_grade_promotion_effective_date.sql`

처리 내용:

1. 기존 `academy_grade_promotion_settings_check`의 1월 1일 고정 제약 제거
2. 실제 달력 범위와 2월 29~31일·4·6·9·11월 31일 제외 제약 추가
3. 기존 기본값 1월 1일 유지
4. 기존 설정과 승급 배치 데이터 유지
5. 설정 변경과 감사로그를 원자적으로 처리하는 함수 추가

원격 Supabase에는 적용하지 않았습니다. 현재 로컬 검증용 Supabase에만 적용했습니다.

## 6. 기준일 계산 방식

기준일은 다음과 같이 계산합니다.

`승급 학년도 + 저장된 월·일`

예:

- 기본값: `2027-01-01`
- 2월 1일: `2027-02-01`
- 3월 1일: `2027-03-01`
- 12월 31일: `2027-12-31`

고정된 시각 보정이나 임의의 하루 더하기·빼기는 사용하지 않습니다.

## 7. 기존 배치 보호 정책

- 설정을 1월 1일에서 3월 1일로 바꾸어도 이미 생성된 배치의 `effective_date`는 변경하지 않습니다.
- 기존 배치가 되돌림 후 다시 미리보기 상태가 되더라도 기존 배치 행을 재사용하고 적용일을 유지합니다.
- 새 학년도의 배치가 처음 생성될 때만 변경된 설정을 스냅샷합니다.
- 설정 변경으로 기존 배치를 삭제하거나 재계산하지 않습니다.
- 승급 배치 대상은 재원·휴원(`paused`/`on_hold`)·퇴원(`withdrawn`) 학생을 모두 포함합니다. 승급 적용 시 학생 상태, 기존 반 배정, 학습기록은 변경하지 않습니다.

## 8. 감사로그 처리

기존 `audit_logs`를 재사용합니다.

- 대상 테이블: `grade_promotion_settings`
- 대상 ID: 학원 ID
- 필드 키: `promotion_settings`
- 이전 월·일과 변경 후 전체 설정 저장
- 변경 관리자와 변경 시각 저장

설정 저장과 감사로그 삽입은 migration에서 추가한 DB 함수의 한 트랜잭션으로 처리합니다.

## 9. 학원별 확장 가능성

설정 테이블의 기본 키가 `academy_id`이므로 현재 구조에서도 학원별로 서로 다른 기준일을 저장할 수 있습니다.

- A학원: 1월 1일
- B학원: 2월 1일
- C학원: 3월 1일

이번 작업에서는 멀티테넌트 권한 구조나 별도 설정 화면을 확장하지 않고, 기존 관리자 학원 범위와 RLS를 유지했습니다.

## 11. 남은 위험 요소

- 자동 승급은 기존 구조와 동일하게 관리자 화면 접근 시점에 실행됩니다. 정확한 시각의 자동 실행을 위한 스케줄러는 이번 작업에서 추가하지 않았습니다.
- 설정 저장 API의 실제 브라우저 저장 동작은 로컬 영속 데이터 변경 없이 검증하지 않았습니다.
- 기존 배치 보호는 `effective_date`를 수정하지 않는 코드와 기존 unique 배치 구조를 유지하는 방식입니다. 실제 배치 생성·설정 변경·재조회 통합 테스트는 별도 테스트 데이터가 필요합니다.
- 로컬 DB는 새 migration을 적용했지만 원격 환경의 migration 적용 결과는 확인하지 않았습니다.

## 12. EC2 배포 전 확인 사항

1. 사용자 승인 후 migration을 원격에 적용할지 별도로 승인합니다.
2. 원격 적용 전 기존 `academy_grade_promotion_settings`와 `grade_promotion_batches` 백업을 확인합니다.
3. 실제 학원별 기준일을 운영자와 확정합니다.
4. 새 배치 생성 전 기준일 표시와 배치 `effective_date`를 확인합니다.
5. 기존 배치의 적용일이 변경되지 않는지 원격 조회로 확인합니다.
6. 설정 저장 감사로그가 함께 남는지 확인합니다.
7. 이후에만 EC2 배포와 실제 운영 적용을 별도로 승인합니다.

이번 작업에서는 EC2 배포, 원격 Supabase migration, 원격 데이터 변경, GitHub push를 수행하지 않았습니다.
